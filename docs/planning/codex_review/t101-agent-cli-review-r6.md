# T-101, ревью r6 (ступень 4)

## Итог

Полный пакет реально выполнен командой `systemd-run --user --scope --unit=rust-tests --slice=rust-build.slice cargo test -j 2`: exit 0, **161/161 lib**, **21/21 CLI**, 0 main и 0 doc. `systemd-run` доступен. Исторические заявления о прогонах r1–r5 и о фактической красноте мутантов M1–M7 этим запуском не подтверждаются: история запусков и сами мутанты не воспроизводились, файлы репозитория не изменялись.

## Finding

**[P1] Не мигрировать существующую БД через `log/intervals sync --create`.** При наличии старой схемы `--create` переводит обе write-команды в `Database::open`, вызывающий `init_schema()` до записи (`src/main.rs:168–189`, `src/db/mod.rs:56–61`). Например, файл со старой таблицей из `tests/cli.rs:243–266`, который без `--create` отвергается, при `log jab --create` получает новые столбцы и таблицы и затем запись. Это обходит отдельную команду `migrate`, для которой требуется согласие владельца: `AGENTS.md:27–34,71–84`. `--create` документирован как инициализация **отсутствующего** файла, а не разрешение на изменение существующей схемы. Для существующего файла требуется existing-only open и отказ с предложением `migrate`; инициализацию оставлять только отсутствующему пути. Тесты не ловят этот путь: помощник `log()` всегда добавляет `--create`, а проверка старой схемы запускает `migrate` явно.

## Чувствительность негативных контролей

- **Пустой/чужой файл без `--create`:** `write_commands_do_not_initialize_existing_file_without_create` реально прошёл. При замене `open_existing` на `open` пустой файл и чужая SQLite БД получают `trainings`; `log` успешно завершается вместо ожидаемого exit 1, и сравнение файла тоже падает. Отдельный unit-тест `open_existing_and_migrate_do_not_create_file` краснеет при возвращении SQLite-флага CREATE. Мутации не применялись; это трассировка кода, не наблюдение мутантного прогона.
- **Чужая строка:** `intervals_sync_cli_is_idempotent_and_fills_once` прошёл. Если убрать фильтр `user_id.is_none()`, запись `start+45 s` попадает между HR-сэмплами 40 и 70 s; `hr_at(0)` и `hr_max(0,45)` дают значения, так что она будет заполнена, а `filled.len()==1` и/или проверка её нулевого пульса упадёт. Это статическая проверка мутанта, не его запуск.
- **Не-watch источник:** `sessions_skip_non_watch_sources` прошёл. Без source-фильтра активность STRAVA дошла бы до `/streams`; mock отдаёт лишь ответ на `/activities`, поэтому запрос streams неуспешен и тест краснеет до `server.join()`. `sessions_skip_close_prefix_sources` аналогично ловит prefix-приём ZEPPELIN. Краснота мутантов оценена трассировкой, не воспроизведена.

## Детерминизм harness

CLI mock слушает `127.0.0.1:0` до запуска процесса (`tests/cli.rs:379–406`): конфликта фиксированного порта нет. Активность начинается за 60 s до логирования, длится 300 s плюс 300 s grace; дата запроса расширена на день в обе стороны. Последний HR-сэмпл 100, а `logged_at` ограничен последним сэмплом, поэтому обычная задержка относительно 70 s не меняет ожидаемый пик. Чужая строка привязана к start+45 s. Остаточная зависимость: если тестовый процесс остановить/усыпить более чем примерно на 9 минут между вычислением start и логированием, CLI-запись окажется вне окна; для обычного CI это не практический флак. Unit mock использует ephemeral-порт и конечное число ответов. Репозиторий после проверки сохранил прежние исходные изменения; тесты могли обновить `target/`, как обычный `cargo test`.
