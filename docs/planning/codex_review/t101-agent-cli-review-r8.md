## Findings

1. **P1 — пустая HR-сессия не должна уступать чужому grace-хвосту** (`src/intervals.rs:93`). При A в `t=0..60` с HR, B в `t=120..420` без HR и сете в `t=150` A всё ещё покрывает сет grace-хвостом. Фильтр `!s.hr.is_empty()` удаляет B *до* выбора ближайшей сессии, поэтому сет получает пульс A, хотя содержащая B должна победить и оставить пульс незаполненным. Заполнение только пустых полей делает ошибку необратимой для следующего sync (контракт `/home/ryazanov/Development/fitness/majowuji/AGENTS.md:90–92`). Текущий тест перекрытия покрывает лишь две сессии с HR; тест пустой HR — лишь одну сессию.

2. **P1 — проверять все используемые колонки `trainings` до допуска записи** (`src/db/mod.rs:173–179`). `schema_is_current` проверяет в `trainings` только четыре добавленные колонки, но `get_trainings` читает ещё `id,date,exercise,sets,reps,notes`. Если в существующей БД удалить, например, `notes`, проверка ошибочно пропустит устаревшую схему. `intervals sync` затем успеет сделать `upsert_watch_session` (`src/main.rs:304–306`) и только на `get_trainings` (`:310–314`) завершится с exit 1: БД уже изменена вопреки правилу, что write-команда не меняет устаревшую схему (`/home/ryazanov/Development/fitness/majowuji/AGENTS.md:27–34`). Проверка полного списка колонок должна предшествовать любому sync-write.

3. **P2 — стабилизировать критерий 0 байт под блокировкой `open_create`** (`src/db/mod.rs:72–99`). Размер проверяется до `BEGIN IMMEDIATE`, а внутри транзакции проверяется только наличие пользовательских объектов. Если после первой проверки другой процесс создаст непустой SQLite-файл только с `PRAGMA user_version=42` (объектов в `sqlite_master` нет), `open_create` инициализирует чужой существующий файл. Транзакция закрывает гонку *между проверкой объектов и записью*, но не гонку размера; это уже не «missing or 0-byte file» по `/home/ryazanov/Development/fitness/majowuji/AGENTS.md:70–76`. Конкурентный `--create` с уже завершившейся инициализацией также может ошибочно отказать вместо обычной записи, если оба вызова увидели 0 байт до захвата блокировки.

4. **P2 — повторить `user_id IS NULL` в самом UPDATE пульса** (`src/db/mod.rs:315–319`). CLI выбирает NULL-строки до расчёта links, но без транзакции. Если бот между выборкой и `fill_training_pulse` выполнит `migrate_trainings_to_owner` (`src/db/mod.rs:511–519`), UPDATE по одному `id` изменит уже не-NULL строку. Это нарушает заявленное ограничение sync на `user_id IS NULL`; миграция NULL-записей ботом прямо описана в `/home/ryazanov/Development/fitness/majowuji/AGENTS.md:102–106`. Условие должно проверяться атомарно с UPDATE.

5. **P2 — ограничить ожидание mock-сервера при пропуске streams** (`src/intervals.rs:463–469`). `spawn_mock` ждёт ровно два TCP-соединения, а тест вызывает `server.join()` до утверждений о результате. Если регрессия фильтра источников пропустит ZEPP, `sessions()` вернёт пустой вектор после первого запроса; поток сервера навсегда останется в `accept()` второго, и тест зависнет вместо красного результата. Это реальная слепая зона негативного контроля: нужна конечная остановка/тайм-аут ожидания или проверка результата до необратимого `join`.
