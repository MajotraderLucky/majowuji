# majowuji T-101 — поведенческое ревью r7

## Итог

Полный прогон `systemd-run --user --scope --unit=rust-tests --slice=rust-build.slice cargo test -j 2` завершился с кодом 0: **161/161 lib, 24/24 CLI**, 0 тестов `main`, 0 doctest. Заявленные автором текущие числа и зелёность подтверждены. В рамках write contract репозиторий не редактировался.

## Findings

1. **P1 — `--create` инициализирует существующий ненулевой чужой SQLite-файл без таблиц.** В `src/db/mod.rs:77–102` признак «пустого файла» подменён отсутствием пользовательских таблиц. Существующий файл с одной `VIEW`, либо SQLite-файл после `CREATE TABLE unrelated; DROP TABLE unrelated`, имеет ненулевой размер, но `user_tables == 0`; `log --create` создаст в нём схему и запишет тренировку. Новый негативный тест использует только чужую **таблицу**, поэтому это не ловит. Нужно различать действительно отсутствующий/0-байтовый файл и уже существующий SQLite-файл без таблиц. Это прямо противоречит [AGENTS.md:74–76](/home/ryazanov/Development/fitness/majowuji/AGENTS.md#L74-L76).

2. **P1 — перекрывающиеся окна двух ZEPP-тренировок могут навсегда привязать неверный пульс.** `link_pulses` (`src/intervals.rs:80–110`) независимо выдаёт ссылку на один и тот же сет для каждой подходящей сессии; `main.rs:315–329` применяет их в порядке API, а `fill_training_pulse` после первого заполнения второе уже не меняет. Например, сессия A закончилась в `t=60`, B началась в `t=120`, сет записан в `t=150`: он попадает и в 300-секундное grace-окно A, и в B. Если API вернёт A первой, будут сохранены пульсы A вместо B, и повторный sync их не исправит. Следует однозначно выбирать сессию для каждого сета до записи; важность первого заполнения подтверждается [AGENTS.md:90–95](/home/ryazanov/Development/fitness/majowuji/AGENTS.md#L90-L95).

3. **P2 — проверка текущей схемы пропускает отсутствие `users`.** `schema_is_current` (`src/db/mod.rs:172–187`) проверяет лишь четыре колонки `trainings` и `watch_sessions`. Если в существующей БД удалить `users`, `list`/`stats` и ветка `log --create` примут её за текущую, хотя `init_schema` создаёт `users` и только `migrate` вправе восстанавливать схему. Нужна проверка этой таблицы/используемых колонок перед разрешением CLI-доступа. Условие устаревшей схемы описано в [AGENTS.md:27–34](/home/ryazanov/Development/fitness/majowuji/AGENTS.md#L27-L34).

4. **P2 — схема может появиться между проверкой и `init_schema`.** В `open_create` (`src/db/mod.rs:77–102`) оба чтения `sqlite_master` и последующее создание таблиц идут отдельными autocommit-операциями. Если второй процесс создаст чужую таблицу или старую `trainings` после `user_tables == 0`, `init_schema` изменит уже существующую чужую/устаревшую БД, несмотря на `--create`; один лишь `SQLITE_OPEN_CREATE` эту гонку не закрывает. Проверку и инициализацию следует сериализовать write-транзакцией. Инвариант «существующая БД не меняется write-командами» задан в [AGENTS.md:32–34](/home/ryazanov/Development/fitness/majowuji/AGENTS.md#L32-L34).

5. **P3 — unit-контроль sync зависит от старого `/tmp`-состояния.** `client_sync_end_to_end_with_mock_api_and_database` (`src/intervals.rs:457–484`) использует `majowuji-mock-<pid>/it.db` без очистки при старте и удаляет каталог лишь в конце теста. Если предыдущий запуск прервался до удаления, а PID повторно выдан процессу тестов, `Database::open` сохранит старый сет с той же фиксированной датой; `links.len() == 1` станет ложным. Нужен уникальный каталог с RAII-очисткой или явное создание свежего файла.

Остаточные исключения — findings 1, 3, 4; поэтому общий контракт пока не закрыт полностью. |

**Чувствительность новых контролей.** Возврат `Database::open` в ветку `may_create` (M8) действительно делает `create_flag_does_not_migrate_existing_outdated_database` красным: `init_schema` добавит колонки/таблицы, затем `log` завершится с 0. `create_flag_does_not_initialize_foreign_existing_file` тоже покраснеет: `Database::open` создаст `trainings` рядом с `unrelated`. `create_flag_writes_existing_current_database` проверяет обратный риск — ложный отказ текущей БД. Заявленные прежние фактические прогоны M8 и живое репро r6 из одного текущего дерева независимо восстановить нельзя; здесь подтверждена логическая чувствительность тестов, а не исторический запуск.

**Свежий путь и гонки.** Отсутствующий файл с `log --create` проверен зелёным `log_create_initializes_new_database`; 0-байтовый файл с `--create` не имеет отдельного теста, но по `open_create` открывается SQLite, `sqlite_master` пуст и `init_schema` выполняется — регрессии не видно. Существующий текущий файл с `--create` проверен отдельным CLI-тестом. Проверка именно открытого SQLite-соединения закрывает простую path-TOCTOU гонку до `sqlite3_open`, но не гонку между проверкой `sqlite_master` и `init_schema` (finding 4).
