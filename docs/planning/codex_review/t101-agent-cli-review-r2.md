# Ревью T-101, раунд r2

## Итог

Патч нельзя считать корректным: `intervals sync` не учитывает пользовательскую изоляцию базы и может записать пульс владельца часов в тренировки другого пользователя; кроме того, production-клиент допускает перенаправление API-ключа на произвольный endpoint из окружения. Также остались граничный false-positive фильтра источников и времязависимый CLI-тест.

## Findings

### [P1] Ограничить связывание пульса владельцем часов

`src/main.rs:294`: `db.get_trainings()` отдаёт `link_pulses` все строки базы, хотя Telegram-бот хранит отдельные `user_id` и по умолчанию допускает до 10 пользователей. Если тренировка второго пользователя попадает во временное окно Zepp-сессии владельца, `fill_training_pulse` необратимо заполнит её пульсом владельца; более того, такая строка сдвинет `set_start` и может изменить вычисление пульса следующего подхода владельца. Нужно связывать сессии только с явно выбранным пользователем/athlete mapping; если sync предназначен владельцу, выборка должна включать владельца и отдельно обоснованные `user_id = NULL`, но не всех пользователей. Репозиторный контракт прямо фиксирует пользовательскую видимость и особый смысл NULL-записей: `/home/ryazanov/Development/fitness/majowuji/AGENTS.md:100-102`.

Точная репродукция по коду: создать owner и второго пользователя, добавить второму training с пустыми pulse в окне возвращённой Zepp-сессии и запустить sync; строка проходит фильтр `t.date >= session.start && t.date <= window_end` в `src/intervals.rs:84-87`, после чего обновляется только по `training_id` в `src/db/mod.rs:225-231`.

### [P1] Не разрешать release-сборке отправлять ключ на произвольный API base

`src/intervals.rs:171-172`: `Client::new` без валидации принимает `MAJOWUJI_INTERVALS_API_BASE` в обычной production-сборке. Поскольку `main` предварительно загружает `.env` (`src/main.rs:124-125`), достаточно оставшегося или подменённого значения вроде `http://host:port`, чтобы обычный `intervals sync` отправил реальный `INTERVALS_API_KEY` этому адресу через Basic Auth (`src/intervals.rs:185-190`), в том числе без TLS. Оверрайд заявлен как тестовый/диагностический, поэтому его следует исключить из release-пути либо защитить явным небезопасным opt-in и проверкой схемы/адреса; локальный mock можно оставить только для test/debug harness.

### [P2] Не принимать любой source с префиксом `zepp`

`src/intervals.rs:150`: проверка `starts_with("zepp")` принимает не только Zepp и ожидаемые алиасы, но и любой независимый source вроде `ZEPPELIN` или `zepp-other`. Такая активность пройдёт фильтр до запроса streams и может навсегда заполнить пустые pulse, хотя заявленный контракт требует отсеивать не-Zepp источники до связывания. Нужен whitelist точных нормализованных значений либо проверка допустимого разделителя после `zepp`; негативный тест должен включать близкий префикс, а не только `STRAVA`. Требование фильтрации и не-перезаписи зафиксировано в `/home/ryazanov/Development/fitness/majowuji/AGENTS.md:86-91`.

### [P3] Убрать зависимость idempotence-теста от скорости машины

`tests/cli.rs:383-387`: mock-сессия начинается в `now - 60s`, а следующий HR sample `(70, 119)` находится всего примерно в 9–10 секундах после времени будущего `log`; при задержке между вычислением `start` и запуском CLI более этого запрошенный peak станет 119, но строка 427 жёстко ожидает 100. На загруженном runner тест может падать без дефекта продукта. Следует строить activity start от уже сохранённой даты training либо сделать HR-фикстуру нечувствительной к задержке.

## Проверка findings r1

1. **Частичная pulse-миграция — исправлено.** Текущий цикл `src/db/mod.rs:148-157` проверяет и добавляет `pulse_before`/`pulse_after` независимо и распространяет ошибку `ALTER TABLE`. `migrate_completes_partially_pulsed_database` создаёт схему только с `pulse_before`, требует успешный CLI migrate и проверяет сохранность значения и появление `pulse_after`.
2. **Не-watch активности — основной дефект исправлен, но фильтр остаётся неполным.** `src/intervals.rs:209-216` отбрасывает `STRAVA` до streams-запроса, а `sessions_skip_non_watch_sources` проверяет ровно один HTTP-вызов. С finding r1 не спорю; новый P2 относится к false-positive выбранного prefix matching.
3. **CLI-идемпотентность — покрытие добавлено.** `tests/cli.rs:375-442` запускает бинарь дважды, проверяет первый fill, пустой второй `filled`, одну строку `watch_sessions` и неизменный pulse. Сам тест содержит отдельную временную хрупкость, описанную выше.
4. **Пустое имя — исправлено.** Тест сначала создаёт валидную БД, затем требует конкретную ошибку `exercise name must not be empty`; выключение guard действительно приводит к успешной вставке и красит тест.

Заявленные результаты прогонов мутантов исторически **не подтверждаемы** из текущего дерева: отдельных mutant patch/log/commit нет. Однако по статической трассировке все три описанных negative control действительно отличают названные старые варианты кода. Равным образом утверждение «159 lib + 20 cli, все зелёные» не перепроверялось запуском: в исходниках статически насчитывается 159 test-атрибутов под `src/` и 20 в `tests/cli.rs`, но write contract запрещает создаваемые Cargo артефакты.
